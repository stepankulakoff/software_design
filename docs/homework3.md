# Домашняя работа №3

Java 17–25, Maven 3.6.3+ и Docker Compose. Перед сборкой запустить Docker Desktop.
Команды находятся в README; Java-процессы запускаются в отдельных терминалах из корня проекта.

## Что изменилось

Два Spring Boot приложения общаются через JSON-RPC 2.0 поверх HTTP.
`rate-provider` возвращает случайный USD/RUB от 85.00 до 94.99. `rate-printer`
раз в 5 секунд читает список адресов из ZooKeeper и выбирает сервер по кругу.
На каждый экземпляр сервера теперь нужен один HTTP-порт, например 8081 или 8082.
RMI и его реестр больше не используются.

ZooKeeper из Compose доступен на `localhost:22181`, записи — `/services/currency-http`.
Это отдельный контейнер: старый ZooKeeper на 2181 не затрагивается.
При завершении сессии серверная запись удаляется. При аварии нужно дождаться тайм-аута.
Клиент обрабатывает пустой список и ошибки связи, затем повторяет попытку.
Если запрос выполняется долго, следующий запуск может задержаться; параллельных запросов нет.
Адреса по умолчанию рассчитаны на локальный запуск Java. Для другого компьютера
задаются `PROVIDER_HOST` и `ZOOKEEPER_ADDRESS`.

## Как работает Pact

1. В `rate-printer` тест `RateClientPactTest` вызывает настоящий `RateClient`, направив его на mock-сервер Pact.
2. Создаётся `rate-printer/target/pacts/rate-printer-rate-provider.json`.
3. На фазе `verify` Maven публикует контракт в локальный Pact Broker.
4. В `rate-provider` тест `ProviderPactIT` на фазе `integration-test` поднимает настоящий HTTP-сервер
   на свободном порту, получает контракты ветки `hw3` из Broker и проверяет каждый запрос/ответ.
5. Результат публикуется обратно в Broker. Несовместимый API, отсутствие контрактов
   или недоступный Broker приводят к ошибке `mvn verify`.

Поэтому обычная полная сборка — `mvn clean verify`. Порядок модулей в корневом POM важен:
сначала клиент публикует контракт, затем сервер его читает. Нужен работающий Broker,
но для контрактных тестов ZooKeeper не требуется: отключается только регистрация тестового сервера.
`mvn test` проверяет локальные тесты, но не выполняет проверку сервера по контрактам из Broker.
`mvn package` также не заменяет `verify`.

Сервер можно собрать отдельно через `mvn -pl rate-provider clean verify`, когда контракт
клиента уже опубликован. Локальных запасных контрактов у сервера нет.
Данные Broker сохраняются в томе PostgreSQL при остановке Compose.

Версии участников Pact по умолчанию получают временную метку сборки, так как локальные
изменения не коммитятся. Для воспроизводимой версии можно передать
`-Dpact.app.version=имя-версии`. Ветку контрактов можно изменить через `-Dpact.branch=имя`;
это метка в Broker, а не создание или переключение Git-ветки.
Адрес Broker переопределяется через `-Dpact.broker.url=http://localhost:9292`.

Контракт требует JSON-RPC версию 2.0, правильный id и числовой result. Число 89.42 в тесте — пример,
а не фиксированный курс: Pact использует числовой matcher.

## Проверка вручную

Запустить два сервера и клиент командами из README. В консоли клиента адреса должны чередоваться.
Остановить один сервер (Ctrl+C): клиент продолжит работу с оставшимся после обновления списка.
Запустить сервер снова: он автоматически появится в балансировке.
Pact Broker доступен в браузере по `http://localhost:9292`.

Проверка несовместимости: временно изменить поле ответа `result` на другое имя в `RateController`,
запустить `mvn -pl rate-provider verify` и убедиться, что сборка падает. Затем вернуть поле обратно.
При таком тесте не изменять клиентский контракт одновременно с сервером.

Spring Actuator, Prometheus и Grafana сюда не входят — это следующая домашняя работа.
